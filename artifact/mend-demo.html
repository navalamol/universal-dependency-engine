The Problem

Manual Mend triage is slow, error-prone, and leaves no audit trail

Every release cycle, a senior engineer re-derives the same semver decisions from scratch. The same npm or Maven knowledge gets re-applied manually, with no record of how decisions were made.

Before — Manual Process (~2–4 hrs)
  • 1
    Download Mend report (Excel/JSON), open file
    Different column layouts per export
  • 2
    For each library: look up CVEs, find fix versions
    10–20 min per library across 8–15 affected packages
  • 3
    Check package-lock.json / Maven tree: direct or transitive?
    Semver range math done in head; major-version conflicts easily missed
  • 4
    Edit package.json overrides or pom.xml manually
    Wrong choice between direct bump vs override causes npm warnings
  • 5
    Run npm install / mvn resolve, verify lock file
    No structured verification — relies on human inspection
  • 6
    Remove stale overrides in future cycles
    Stale overrides accumulate silently; no record of when each was added

  • ✓
    One command reads JSON or Excel — auto-detects format and ecosystem (npm vs Maven)
  • ✓
    SemVer engine computes the minimum safe fix that covers every CVE for each library
  • ✓
    Dep tree parsed from package-lock.json — direct vs transitive correctly identified; range violations detected
  • ✓
    Phase A applied automatically; Phase B/C surface justification text and a structured review doc
  • ✓
    npm install runs, lock file re-parsed, every Phase A version confirmed present
  • ✓

Architecture

Six-stage pipeline — one file, one responsibility

Data flows in one direction. Each stage has a single job; no stage reaches into another's output. The optional registry step enriches version data in-flight before classification.

Stage File Owns
Parse src/parser.js Mend JSON + Excel → LibraryEntry[] — groups multi-CVE entries by keyUuid
SemVer Engine src/semver-engine.js Deterministic fix-version resolution per library — per-CVE minimum, then max across CVEs
Phase Classifier src/phases.js A/B/C classification + justification; promotions/demotions with dep tree; false-positive flags
Output Writer src/overrides.js · src/pom-writer.js npm: writes overrides.json + mutates package.json. Maven: writes pom-patch.xml + mutates pom.xml
Report src/report.js Generates remediation-report.md — display only, zero business logic
Phase Confidence Model

Every CVE is classified before any file is touched

The three-tier model separates what is safe to automate from what requires human judgement. Phase determines both the output artifact and the required action — nothing auto-applies below 95 % confidence.

A
95–100 % confidence
Auto-Apply
  • Same-major patch or minor upgrade
  • Single instance in the dependency tree
  • All consumer semver ranges satisfied
  • Version confirmed on registry (optional)
Output phase-a-overrides.json (npm) phase-a-pom-patch.xml (Maven)
No human action required
B
60–95 % confidence
Review First
  • Multiple same-major instances in tree
  • Consumer range violates the fix version
  • Nested parent-scoped override needed
  • Promoted from C via dep tree analysis
Output phase-b-overrides.json (npm) phase-b-pom-patch.xml (Maven)
Review justification, then apply
C
<60 % confidence
Human + Claude Triage
  • MAJOR_BUMP — e.g. nanoid 3 → 5
  • NO_FIX — no patch available
  • Multi-major version conflict in tree
  • Consumer range unresolvable by override
Output phase-c-review.md — with justification template
Structured triage via CLAUDE_WORKFLOW.md
Phase promotions and demotions run automatically when a dep tree is available. A Phase B item is promoted to A if all consumer ranges are verified compatible. A Phase A item is demoted to B if any consumer pins a range that the fix version cannot satisfy. Multi-major Phase C items are promoted to B when the dep tree shows each major line is consumed by a disjoint set of parent packages, enabling nested parent-scoped overrides.
End-to-End Workflow

Same command structure, any ecosystem

Auto-detects npm vs Maven from the report's library.type field. Override with --ecosystem if needed.

# Dry run — see what would change
node mend-fix.js --report GH_ui-platform_dev-vulnerability-report.json --dry-run

# Auto-apply Phase A with dep tree + registry verification
node mend-fix.js --report GH_ui-platform_dev-vulnerability-report.json \
  --package-json ./package.json \
  --lock-file    ./package-lock.json \
  --verify-versions
1
Parse report
Reads Mend JSON/Excel, groups all CVEs per library by keyUuid, normalises fix-resolution strings into versioned arrays.
8 libraries · 22 CVEs (ui-platform example)
2
Build dep tree from package-lock.json
Parses v2/v3 flat packages map. Tracks each package's parents, their declared semver ranges, and whether the path is dev-only. Enables range validation and false-positive detection.
3
Resolve fix versions
For each CVE, finds the minimum same-major fix > current. Takes the max of per-CVE minimums — one version that covers every CVE. Escalates to MAJOR_BUMP if no same-major fix exists.
4
Classify into phases (with promotions)
Assigns A/B/C based on upgrade type, tree structure, and consumer range compatibility. Promotes B→A and C→B where the dep tree confirms safety.
Phase A: 5 · Phase B: 0 · Phase C: 3 (ui-platform example)
5
Detect direct deps vs transitive
Phase A items with no transitive consumers are bumped directly in dependencies/devDependencies. Transitive packages go into overrides.
6
Apply to package.json + run npm install
Snapshots both files. Writes Phase A changes. Runs npm install --legacy-peer-deps --package-lock-only. Re-parses lock to confirm every fixed package resolves to ≥ recommended version. Saves manifest for future runs.
phase-a-overrides.json · phase-b-overrides.json · phase-c-review.md · remediation-report.md
Rollback on failure: Both package.json and package-lock.json are snapshotted before any mutation. If npm install fails or verification finds unresolved packages, both files are restored exactly. The repo is always left in a known-good state.

# Auto-apply Phase A to pom.xml with Maven Central verification

Parse Maven report
Detects MAVEN_ARTIFACT library type. Extracts groupId and artifactId. Handles Maven version strings (e.g. 1.84 coerced to 1.84.0) and GAV coordinate format.
2
Resolve fix versions (same SemVer engine)
Identical algorithm to npm — minimum same-major fix per CVE, max across CVEs. The SemVer engine is ecosystem-agnostic.
3
Verify on Maven Central
Queries Maven Central Solr API per artifact. Finds nearest published version ≥ fix version in the same major. Sequential with 300 ms delay to avoid rate limits.

Classify into phases
Same Phase A/B/C rules. Note: Maven dep-tree parsing is not yet implemented, so B→A promotion and range validation are npm-only at this stage.
5
Apply to pom.xml
Writes a <dependencyManagement> patch. If --pom-xml provided, applies in-place: updates existing <version> tags or inserts new <dependency> entries. Creates the section if absent.
phase-a-pom-patch.xml · phase-b-pom-patch.xml · phase-c-review.md · remediation-report.md

Runs mvn dependency:resolve -B -q to confirm the patched pom resolves cleanly. Saves manifest for idempotency on subsequent runs.
Rollback on failure: The original pom.xml content is held in memory before any writes. Any exception — including a failed mvn resolve — restores the file immediately. The manifest ensures manually-edited versions are never silently overwritten on re-run.

Gaps & Next Steps

Honest gaps — scoped to Mend remediation

These are the remaining pieces within the existing scope. No roadmap expansion — only closing gaps in what's already planned.

1

Maven dep-tree parser

The npm path uses package-lock.json for consumer range validation, B→A promotion, and dev false-positive detection. Maven has no equivalent yet. Parsing mvn dependency:tree output or the pom's effective POM would unlock Phase B promotions and scope-based false-positive classification for Java projects.

2

Deeper mixed dev/runtime chain classification

False-positive detection currently fires only when all dep chains to a package are dev-only. A package with one runtime path and one dev path is not flagged. Per-chain analysis would give a more precise signal and surface partial false positives with evidence.

3

mendfix analyze / mendfix apply subcommands

The current CLI uses flags (--dry-run, --package-json) to switch between modes. Named subcommands would make the intent explicit and allow the help text to be per-mode, reducing the chance of invoking apply accidentally.

4

Auto git commits by confidence tier

Phase A changes are fully automated and should commit automatically with a structured message. Phase B/C changes need human review before committing. Separating the commit flow by tier keeps the git history clean and makes rollback straightforward.

5

Broader Excel column auto-mapping

The parser uses fuzzy substring matching to find column names in Mend Excel exports. Different Mend configurations and export versions produce different column headers. More test cases across team exports would harden this detection.

Under the Hood

Key algorithms

Two functions carry most of the logic. Everything else is plumbing around them.

Fix Version Resolution
src/semver-engine.js — resolveFixVersion(entry)
// For each CVE: find the minimum same-major fix > currentVersion.
// Take the MAX of those per-CVE minimums — one version that covers every CVE.
// If any CVE has no same-major fix, escalate to MAJOR_BUMP.
function resolveFixVersion(entry) {
  const { currentVersion, cves } = entry;
  const perCveMinimums = [];

  for (const cve of cves) {
    const sameMajorFixes = cve.fixVersions.filter(v =>
      semver.major(v) === semver.major(currentVersion) &&
      semver.gt(v, currentVersion)
    );

    if (sameMajorFixes.length === 0) {
      return resolveMajorBump(entry); // no same-major path — MAJOR_BUMP
    }

    const min = sameMajorFixes.reduce((a, b) => semver.lt(a, b) ? a : b);
    perCveMinimums.push(min);
  }

  // Highest of the per-CVE minimums — satisfies every CVE simultaneously
  const recommendedVersion = perCveMinimums.reduce((max, v) =>
    semver.gt(v, max) ? v : max
  );
  return { recommendedVersion, upgradeType: 'SAFE' };
}
This function runs independently per library entry. No AI, no heuristics — the semver package does all comparison. The "take max of per-CVE minimums" step is the key insight: it ensures the single chosen version fixes every CVE the library has, not just one.
Phase Classification
src/phases.js — classifyPhase(item, allItems)
// Hard rules first — these never move regardless of dep tree.
function classifyPhase(item, allItems) {
  if (item.upgradeType === 'MAJOR_BUMP') return { phase: 'C', reason: 'MAJOR_BUMP' };
  if (item.upgradeType === 'NO_FIX')    return { phase: 'C', reason: 'NO_FIX' };

  // Same package at multiple major versions → single overrides key can't cover both.
  const samePackage = allItems.filter(i => i.libraryName === item.libraryName);
  const majors = new Set(samePackage.map(i => semver.major(i.currentVersion)));

  if (majors.size > 1) return { phase: 'C', reason: 'MULTI_MAJOR_CONFLICT' };

  // Multiple instances, same major — safe to override but worth a review.
  if (samePackage.length > 1) return { phase: 'B', reason: 'MULTI_INSTANCE' };

  // Single instance, same-major upgrade — auto-apply candidate.
  return { phase: 'A', reason: 'SAFE_SINGLE_INSTANCE' };
}
Base classification without the dep tree. A second pass in applyPhases() uses the parsed package-lock to run demotions (consumer range violation → A to B) and promotions (all ranges compatible → B to A; disjoint multi-major parents → C to B with nested overrides). The hard rules — MAJOR_BUMP and NO_FIX stay at C — cannot be promoted by any dep tree evidence.
