Phase 6 — Step 1

MendFix VS Code Extension

Analyze vulnerability reports from Mend, Snyk, Dependabot, and nine other providers directly inside VS Code — without leaving your editor.

v0.1.0 VS Code ^1.85 Node.js ^18 Plain JS — no build step

Overview

MendFix is a Node.js CLI engine that reads vulnerability reports and automatically remediates ~90–95% of CVEs via npm overrides or Maven dependencyManagement patches. This VS Code extension wraps that engine in a sidebar panel so you can analyze reports, see phase-classified results, and (in Step 2+) apply remediations — all without opening a terminal.

Phase A
95–100% confidence
Same-major patch/minor. Safe to auto-apply. Output: phase-a-overrides.json
Phase B
60–95% confidence
Multiple same-major versions or forced override. Review before applying.
Phase C
<60% confidence
Major version bump, no fix, or multi-major conflict. Manual review required.
✓
Nine providers supported: Mend, Snyk, npm-audit, Dependabot, OWASP, OSV, Trivy, GitLab, and Xray. Drop any of their JSON outputs onto the panel — provider detection is automatic.

Installation

Option A — Open the extension folder in VS Code (development mode)

This is the fastest path. No packaging needed. Open the packages/vscode-extension folder directly in VS Code and press F5 — VS Code launches an Extension Development Host with MendFix loaded. 

# from the project root
code packages/vscode-extension

Then press F5 (or run Run MendFix Extension from the Run & Debug panel). A new VS Code window opens with the extension active.

Option B — Install from .vsix

Package the extension and install it into your regular VS Code instance:

cd packages/vscode-extension
npm install          # installs @vscode/vsce (dev dep only)
npx vsce package     # produces mendfix-vscode-0.1.0.vsix

Then in VS Code: Extensions → … → Install from VSIX…

⚠
Important for Option B: The extension requires the MendFix engine to be present at ../../mendfix.js relative to the extension folder (i.e., the project root). The engine is not bundled into the .vsix. Install the .vsix only from within the project checkout, not as a standalone tool.

Quick Start

1
Open the MendFix panel

Click the shield icon in the Activity Bar (left sidebar). The MendFix panel opens. Alternatively, run the command MendFix: Open Panel from the Command Palette (Ctrl+Shift+P / ⌘⇧P).

2
Select a vulnerability report

Click Browse and select a JSON report from Mend, Snyk, Dependabot, npm-audit, or any supported provider. Or right-click any .json file in the Explorer and choose MendFix: Analyze Vulnerability Report.

3
Click Analyze

MendFix parses the report, runs the SemVer resolution engine, and classifies each library into Phase A, B, or C. Results appear in the panel within seconds.

4
Read the results

The summary cards show library counts per phase. The library list below shows each library's current version, recommended version, CVE count, and highest severity. Phase A items are safe to auto-apply in Step 2.

The MendFix Panel

The panel lives in the VS Code Activity Bar sidebar. It uses VS Code's WebviewViewProvider API, which means it's always available at the click of the shield icon — no tab management, no floating windows.

Controls

ControlWhat it does
Browse Opens a file picker filtered to .json files. Picks the vulnerability report to analyze.
Verify registry versions When checked, MendFix queries the npm registry to confirm recommended versions exist before displaying them. Slower but more accurate for offline-first environments.
Analyze Runs the full analysis pipeline: parse → resolve → phase-classify. Enabled once a file is selected.
⚙ MendFix settings Opens VS Code Settings filtered to the mendfix.* namespace. Appears after the first successful analysis.

Right-click shortcut

Right-clicking any .json file in the Explorer sidebar shows MendFix: Analyze Vulnerability Report. This pre-loads the file path into the panel and focuses it — one click instead of three.

Analyzing a Report

The analyze pipeline runs entirely in the VS Code Extension Host process (Node.js). No network calls are made unless you check Verify registry versions. Nothing is written to disk during analysis — output files are generated only when you click Apply (Step 3).

Understanding Phase A / B / C

Every library in the results is classified into one of three phases. The classification is deterministic — it uses the semver package, never an LLM.

PhaseConditionActionOutput file
A Same-major patch/minor upgrade, single version in the dependency tree Safe to auto-apply without review phase-a-overrides.json
B Multiple same-major versions present, or parent upgrade is preferred path Review the override before applying phase-b-overrides.json
C Major version bump required, no fix exists, or multi-major version conflict Manual remediation with justification manual-review.md
⚠
Hard rule: MAJOR_BUMP is always Phase C. A package like nanoid 3→5 introduces breaking API changes that cannot be safely handled by an override alone. Phase C items are never auto-applied.

What Changed & Why (scaffold → rework)

The original scaffold used the wrong VS Code panel API. The rework corrected three distinct problems. Each is explained below so future contributors understand the decisions.

1. WebviewPanel → WebviewViewProvider

The scaffold created a WebviewPanel — a floating tab in the editor area that VS Code only shows when code explicitly calls createWebviewPanel(). There was no Activity Bar icon, no persistent sidebar location, and the panel vanished when the user switched tabs. The correct API for a persistent sidebar tool is WebviewViewProvider, registered against a view declared in contributes.views. VS Code then manages the panel's lifecycle: it appears as the shield icon in the Activity Bar, persists across tab switches, and reopens automatically after a window reload.

Scaffold (wrong)Rework (correct)
vscode.window.createWebviewPanel()window.registerWebviewViewProvider()
No Activity Bar iconShield icon via contributes.viewsContainers.activitybar
Tab panel, disappears on tab switchSidebar panel, always accessible
No contributes.views declarationView declared with type: "webview"

2. Wrong provider API: parseReport → detectProvider + getParser

The scaffold called require('src/providers/index.js').parseReport(path). This function does not exist. src/providers/index.js exports { detectProvider, getParser, PROVIDER_NAMES } — the two-step auto-detection API. parseReport lives on each individual provider module (e.g. mend.parseReport, snyk.parseReport) and is accessed via getParser(provider).parseReport(path). The fix: 

// Wrong (scaffold)
const { parseReport } = require(PROVIDERS_PATH);  // ❌ undefined

// Correct (rework)
const { detectProvider, getParser } = require(PROVIDERS_PATH);
const provider = detectProvider(reportPath);       // auto-detect: mend/snyk/npm-audit/…
const entries  = getParser(provider).parseReport(reportPath);

3. verifyVersions was received but not forwarded

The panel accepted the verifyVersions checkbox value from the webview but never passed it to the engine. Registry verification in mendfix.js is a separate step that runs after buildResolutionPlan() by calling verifyPlanVersions(plan) from src/ecosystems/npm/registry.js. The panel now replicates this: 

let plan = buildResolutionPlan(entries);
if (verifyVersions) {
  const { verifyPlanVersions } = require(REGISTRY_PATH);
  plan = await verifyPlanVersions(plan);           // stamps registryExists on each item
}
const phasedItems = applyPhases(plan, null);

Apply Workflow (Phase 6 Step 3)

Analyze is a read-only operation — it never writes files or runs installs. The Apply flow (arriving in Step 3) takes the analyzed results and actually patches the repo. Here is the complete end-to-end flow so you can understand what settings to configure and what to expect.

1
Analyze → confirm Phase A/B/C split

Run Analyze first. Verify Phase A contains the libraries you expect and Phase C items have been acknowledged. Apply will refuse to run if no Phase A items exist.

2
Set Repo target (package.json + lock file)

Expand the Repo target section. Browse to the package.json of the target repository and its package-lock.json. These are required for npm apply. Maven requires pom.xml (configured in settings: mendfix.pomXml).

3
Click Apply Phase A

The extension host calls the engine apply path — no shell, direct require():

  • src/ecosystems/npm/overrides.js — writes overrides block into package.json
  • src/ecosystems/npm/installer.js — runs npm install, verifies lockfile resolves correctly, rolls back on failure
  • src/core/graph-diff.js — captures before/after lockfile diff, writes graph-diff.md
  • If Auto-commit: src/core/git-commits.js commits the changes
  • If Open PR: platform-specific poster opens a PR/MR via the CI/CD API
4
Progress stream

The extension host streams progress lines to the webview via { type: 'applyProgress', line } messages. The panel displays them in a scrolling log area. On completion: { type: 'applyResult', written, committed, prUrl }.

5
Review output files

Output is written to mendfix.outDir (default ./mendfix-output/): remediation-report.md, graph-diff.md, phase-a-overrides.json. Phase B and C outputs are written for review but not applied unless Apply Phase B is enabled.

⚠
Before Apply: ensure the working tree is clean (no uncommitted changes). The engine checks this before writing. If Auto-commit is enabled, the commit will include only the MendFix-generated changes — a dirty tree will cause the commit step to abort and roll back.

All Settings & Their CLI Equivalents

Every VS Code setting maps 1:1 to a CLI flag. The table below is the complete reference. Settings are workspace-scoped (per-repo), never user-scoped — each repository has its own values. Platform tokens are not in settings; they are stored securely via vscode.SecretStorage and never written to settings.json.

SettingCLI flagDefaultWhen to set
mendfix.outDir --out-dir ./mendfix-output Always — controls where output files are written.
mendfix.verifyVersions --verify-versions false Enable when you need to confirm recommended versions actually exist in the registry. Adds ~2–5s.
mendfix.packageJson --package-json empty npm repos. Path to the package.json to patch with overrides. Required for npm Apply.
mendfix.lockFile --lock-file empty npm repos. Enables dep-tree features: dev/runtime classification, parent upgrade recommendations, consumer range validation.
mendfix.pomXml --pom-xml empty Maven repos. Path to pom.xml for <dependencyManagement> patches.
mendfix.ecosystem --ecosystem auto Override auto-detection only when the report has mixed library types or detection is wrong.
mendfix.applyPhaseB --apply-phase-b false Enable after manually reviewing phase-b-overrides.json. Phase B overrides cover multi-version scenarios — review before applying.
mendfix.autoCommit --commit false Auto-commit Phase A fixes. Requires a clean working tree. The commit message is auto-generated from the CVE summary.
mendfix.autoCommitPhaseB --commit-phase-b false Auto-commit Phase B fixes. Requires mendfix.applyPhaseB to also be enabled.
mendfix.dryRun --dry-run false Show the remediation plan in the panel without writing any files or running npm install. Safe to enable permanently during exploration.
mendfix.verbose --verbose false Print the Safety Gate pre-edit checklist for every item during apply. Useful for auditing what the engine checked before writing.
mendfix.openPr --open-pr false Open a PR/MR on the CI/CD platform after a successful apply. Requires mendfix.platform and a stored token.
mendfix.platform --platform empty Set to github, gitlab, azuredevops, or bitbucket. The corresponding token must be stored via the panel's token prompt (SecretStorage).
mendfix.prBase --pr-base main Target branch for the opened PR. Change to develop or your repo's default if it differs.
ℹ
Platform tokens (GitHub, GitLab, Azure DevOps, Bitbucket) are never stored in settings.json. They are entered once via a secure input prompt in the panel and stored in vscode.SecretStorage — encrypted by the OS credential store, never written to disk in plaintext.
