The Core Problem With the Current State

Everything we've built is correct and powerful, but it's invisible. The engine can do things no other tool does — but right now the only way to see it is reading markdown files in a terminal. That's a demo that impresses engineers but loses executives and security leads in 30 seconds.

Your instinct is right: the product needs a proof-of-value moment that is undeniable. Here's how I'd think about the full picture.

---

The "Wow" Moment Needs Three Things to Co-exist

Rich, realistic input   →   Engine does the impossible   →   UI makes it obvious
(fixtures + reports)        (Phase A/B/C + paths)              (extension / dashboard)

All three have to be ready at the same time. A great engine with weak fixtures produces unimpressive numbers. Great fixtures with no UI means executives see a terminal. A beautiful UI with toy data gets dismissed in the first question.

---

My Prioritization

Priority 1 — The Demo Corpus (Before Anything Else)

This is the foundation everything else sits on. Without it, Phase 6 UI has nothing compelling to show.

What it needs to be:
- A synthetic but realistic monorepo: one package.json + package-lock.json, one pom.xml, maybe a requirements.txt
- Designed so the transitive tree has depth — the vulnerable packages are 2-3 levels deep, not direct deps
- The direct dep tree is clean — a naive scanner sees nothing alarming at the surface
- The lock file is constructed so that upgrading 3-4 parent dependencies each transitively eliminates 10-15 CVEs
- 60-80 total CVEs across the corpus, spanning all severity levels

What this proves:
- Snyk/Dependabot suggest: "Upgrade these 18 direct deps" — many of which are major bumps or have no fix
- We say: "Upgrade these 4 parents (Phase A, safe, auto-applied), and you close 52 CVEs in one npm install. Here are the 12 that need migration plans. Here are 8 that are test-only and not reachable in production."
- That delta — 18 suggestions → 52 CVEs closed automatically — is the product.

What to build:
- fixtures/demo-corpus/ directory with the package files
- Multi-scanner reports all pointing at the same corpus: one Mend JSON, one Snyk JSON, one Dependabot JSON, one OSV JSON — same vulnerabilities, different formats — so you can demo "works with every scanner you already have"
- A mendfix demo subcommand that runs the full pipeline against the corpus and produces the showcase output in one command

---

Priority 2 — The Comparison Narrative Module

The numbers mean nothing without a frame. We need a module that produces a side-by-side:

| Scanner Recommendation      | This Tool                                    |
|-----------------------------|----------------------------------------------|
| 18 direct upgrade suggestions | 52 CVEs closed automatically (Phase A)     |
| 6 "no fix available"        | 4 resolved via parent upgrade (Phase B)     |
| 5 major bumps (manual)      | Migration plan + effort estimate (Phase C)  |
| 0 exposure context          | 8 flagged as test-only / not reachable      |
| 0 evidence trail            | Full SARIF + VEX export for every finding   |

This is what you put on slide 2 of a demo. Every security exec immediately asks "why don't our existing tools do this" — and the answer is "because they scan manifests, not lock files, and they don't model the transitive dependency graph."

This is a src/core/comparison-report.js module — takes the raw scanner output and our phasedPlan, produces the delta table. About a day of work but extremely high leverage.

---

Priority 3 — Phase 6 UI (But Scoped Right)

The VS Code extension already exists and M1.3 fixed the pipeline gap. The rebuild doesn't need to be ambitious — it needs to be demo-ready:

- Panel 1: Scan — drag in any scanner report or point at a directory; shows the "before" picture (what the scanner found)
- Panel 2: Analyze — one click runs runAnalysisPipeline; shows Phase A/B/C breakdown with the comparison table
- Panel 3: Apply — Phase A applies with one click; shows the graph diff (which packages changed)
- Panel 4: Evidence — for each finding, shows the full evidence bundle: CVEs, exposure, verification status, remediation path

That's it. Four panels. No configuration required for the demo path.

The reason to do UI third (not second) is that Panel 2's comparison table only lands if the corpus numbers are real. If the demo corpus shows 4 CVEs, the UI looks like any other tool.

Priority 4 — Points You Didn't Mention (But Matter for the Demo)

Exposure classification in the report. The "8 findings are test-only" number is only credible if the report shows why — the dep chain, the package name pattern, the lockfile dev flag. This is already built in D1A; it just needs to be surfaced prominently in the output.

The "one command" demo path. The security expert sitting across from you during a demo does not want to set up a config file. mendfix demo should pull the corpus, run everything, and open the VS Code panel in one step. First demo experience defines the product perception.

The SARIF import story. Every enterprise security team already has a SIEM or a DAST platform that ingests SARIF. The fact that we export SARIF means "fits into your existing workflow." That's a procurement unlock, not a technical detail. It should be on a slide.

False positive suppression. The corpus should include 5-6 findings that are flagged as probable false positives (dev-only, test framework, CI tool). Showing that we don't recommend fixing those — while competitors fire alerts on them — is a strong differentiator. "Less noise" is as valuable as "more fixes."
