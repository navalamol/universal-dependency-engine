# Claude Mend Triage Workflow

Feed this file to Claude alongside the Mend report and package-lock.json to run the remaining 5-10% of manual triage that the automation script cannot do deterministically.

**Pre-condition:** Run `mend-fix.js` first. This document covers only the items the script escalated to `manual-review.md`.

---

## What you need to give Claude

```
Files:
  mend-output/manual-review.md     (generated by mend-fix.js)
  package-lock.json                 (from the target project)
  package.json                      (from the target project)
  mend-output/phase-a-overrides.json (so Claude knows what is already handled)

Prompt:
  "Follow CLAUDE_WORKFLOW.md. Here are the Phase C items: [paste manual-review.md].
   package-lock.json: [paste or attach].
   Produce: updated package.json overrides (Phase B/C decisions), 
   false positive justifications, and commit messages."
```

---

## Step 1 — Read context

Before analysing any item, Claude must:

1. Read `phase-a-overrides.json` — understand what is already fixed.
2. Read `package-lock.json` — the source of truth for resolved versions and dependency chains.
3. For each Phase C item, locate it in `package-lock.json`:
   ```
   grep -A5 '"<package>"' package-lock.json
   ```
   Find: the resolved version, the `requires` field of its parent, and whether `"dev": true` is set.

---

## Step 2 — MAJOR_BUMP items

For each item with `upgradeType: MAJOR_BUMP`:

### 2a. Check if a direct dependency can be upgraded instead

In `package-lock.json`, find all packages that list `<package>` in their `requires`. Walk up the chain until you reach a direct dependency (something listed in root `package.json` `dependencies` or `devDependencies`).

Decision tree:
```
Is there a newer version of the PARENT that ships the fixed child version?
  YES → Recommend upgrading the parent. Do NOT add an override.
  NO  → Override is the only option. Proceed to 2b.
```

### 2b. Assess API compatibility for the override

Check the package's changelog (GitHub releases page or CHANGELOG.md) for breaking changes between the current major and the recommended major.

Look for:
- Removed exports or renamed functions
- Changed function signatures
- New peer dependency requirements
- Node.js version requirement changes

Search the project codebase for all import/require calls:
```bash
grep -r "require\(['\"]<package>" src/
grep -r "from ['\"]<package>" src/
```

Classify:
- **No breaking change affects this project** → add to Phase B overrides with note "API compatible"
- **Breaking change exists but no affected call site** → add to Phase B with note "breaking change in unused API"
- **Breaking change affects call site** → stays Phase C, document specific breaking change and file:line

### 2c. Output

For items that can be overridden: add to `package.json` overrides section.
For items that cannot: write a justification entry (see Step 4 template).

---

## Step 3 — Multi-version conflict items

For each item where two major version lines of the same package are present:

### 3a. Identify all consumers

Run (or simulate from package-lock.json):
```bash
npm ls <package>
```

In `package-lock.json`, find every package whose `requires` includes `<package>`. Group by the major version range they request:
```
1.x consumers: [list of packages]
2.x consumers: [list of packages]
```

### 3b. Check if parents can be upgraded

For each consumer group, check if the parent package has a newer version that updated its `<package>` dependency to the fixed version.

If yes: recommend upgrading the parent. This naturally pulls in the fixed version without an override.

### 3c. Use nested overrides if parent upgrade is not possible

npm supports nested overrides keyed by parent package:
```json
"overrides": {
  "parent-package": {
    "<vulnerable-package>": "<fixed-version>"
  }
}
```

This patches only that parent's dependency without affecting other consumers.

Write one nested override block per consumer group. Test that the ranges are compatible:
- Consumer requires `"<package>": "^1.0.0"` and fix is `1.1.18` → compatible, safe to override.
- Consumer requires `"<package>": "^1.0.0"` and only fix is `2.x` → major bump, document risk.

---

## Step 4 — False positive assessment

For items with `upgradeType: NO_FIX` or where no safe path exists:

### 4a. Build the full dependency chain

In `package-lock.json`, find every path from a root dependency to the vulnerable package. Document as:
```
<root-dep> → <mid-dep> → <vulnerable-package>
```

### 4b. Classify each chain as runtime or build/dev

Check the root dependency of each chain:
- If it appears in `devDependencies` in `package.json` → **build/dev chain**
- If it has `"dev": true` in `package-lock.json` → **build/dev chain**
- Otherwise → **runtime chain**

### 4c. Decision

```
ALL chains are build/dev only?
  YES → False positive. Write justification (template below).
  NO  → At least one runtime chain exists. Cannot classify as false positive.
         Document the runtime chain and escalate.
```

### 4d. False positive justification template

```markdown
## False Positive: <package>@<version> — <CVE-ID>

**Vulnerability:** <one-line description from CVE>
**Justification:** This package is used exclusively in the build pipeline and 
is not part of the deployed application bundle.

**Dependency chains (all build-time):**
- <root-dep> (devDependency) → <mid> → <package>
- <root-dep> (devDependency) → <package>

**Evidence:**
- `<root-dep>` is listed under `devDependencies` in package.json
- `<package>` does not appear in the production bundle (`npm ls --omit=dev`)
- No upstream fix is currently available

**Risk:** None to production. Monitored for upstream patch.
**Action:** Accept risk. Re-evaluate when a fix is published.
```

---

## Step 5 — Remove unnecessary overrides after npm install

After `npm install --package-lock-only --legacy-peer-deps`, check each override:

For each entry in `package.json` overrides:
```bash
npm ls <package>
```

If the resolved version in `package-lock.json` matches or exceeds the override version **without** the override being required (i.e., the parent package's semver range naturally resolves to the fixed version), remove the override entry.

Example:
```
Override: "postcss": "8.5.23"
After install: parent package requires "postcss": "^8.5.0" and resolves to 8.5.23 naturally
→ Remove the override. The constraint is no longer needed.
```

Keep the override only if removing it causes the lockfile to resolve back to a vulnerable version.

## Step 6 — Commit structure

Produce three separate commits:

**Commit 1 — Phase A (auto-applied by script)**
```
fix(deps): apply Phase A security overrides

Semver-compatible patch/minor upgrades, 95-100% confidence.
No breaking changes expected.

Packages:
- <package>: <from> → <to> (<CVE-IDs>)
...
```

**Commit 2 — Phase B/C overrides after manual review**
```
fix(deps): apply Phase B/C overrides after manual triage

Reviewed: API compatibility, parent chain, semver ranges.

Packages:
- <package>: <from> → <to> — <one-line reason it is safe>
...
```

**Commit 3 — False positive justifications (docs only)**
```
docs(security): add false positive justifications for unfixable CVEs

No code change. Justifications recorded for audit trail.

Packages:
- <package>@<version>: build-time only, no runtime exposure
...
```

---

## What Claude should NOT do

- Do not add overrides for MAJOR_BUMP items without checking call sites first.
- Do not classify as false positive without tracing ALL dependency chains.
- Do not remove overrides without verifying the lockfile resolves correctly without them.
- Do not produce a single large commit — the three-commit structure is required for review clarity.
